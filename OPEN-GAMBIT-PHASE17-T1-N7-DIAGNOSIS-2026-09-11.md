## 1. The question T1 had to answer

Phase 1.6 recorded **N7**: two limits that configuration cannot raise.

| Limit | Value | Where |
| --- | ---: | --- |
| `tokenBudget` clamp ceiling | 8,000 | `getGambitModelRoleConfig` (`llm.ts:98`) |
| non-translation `timeoutMs` clamp ceiling | 30,000 ms | `getGambitModelRoleConfig` (`llm.ts:96`) |

And it recorded that the critic's residual failure shape *changed* when the budget
went from 3,000 to 6,000: at 3,000 the truncations died in ~15 s, at 6,000 they died
at **28.5–30.3 s**, including one hard `timeout`. Phase 1.6 measured a successful
critic call at **29.4 s**.

Two mutually exclusive root causes fit that description, and they demand **opposite**
fixes:

- **(a) still token-bound** — the model needs more than 6,000 tokens and is stopped by
  `finish_reason=length`. The ~30 s observation time is simply *how long it takes to
  generate 6,000 reasoning tokens*. Raising the deadline would help nothing.
- **(b) now deadline-bound** — the model would have finished, but the 30,000 ms clamp
  kills the socket first. Raising the token budget would help nothing.

Implementing 方案 i (bounded re-sampling) on a (b) diagnosis would be treating a
symptom; implementing 方案 ii (raise the deadline) on an (a) diagnosis would be
wasted risk. T1 exists to separate them before either is built.

## 2. Method

Matrix B only (forced admission), critic 6,000 / analysis 8,000 / triage 2,400, role
`timeoutMs` = the 30,000 ms clamp, 4 Phase-1-admitted candidates × replicates.

Separating the two hypotheses needs one thing Phase 1.6 could not do from its summary
console alone: for **every failed critic call**, whether the captured SSE stream ended
with `finish_reason=length` (token wall) or was cut with no terminal frame / an
explicit `timeout` (deadline wall). The probe's fetch-`tee` observation layer already
captures the trailing frames, so the classification is read from the transport, not
inferred from elapsed time.

The probe asserts rather than assumes its own premises:

```
expect(criticRole.tokenBudget).toBe(CRITIC_BUDGET);     // not silently clamped
expect(criticRole.timeoutMs).toBe(ROLE_TIMEOUT_MS);      // the clamp is where N7 says
```

Chunked per N8 (≤10 replicates and ≤24 observed HTTP requests per process), with each
block persisted to disk after **every** replicate so a degrading process cannot destroy
an earlier block's evidence. Two blocks were run, each in a **fresh process**.

## 3. Result

### 3.1 Failure classification — the decisive number

Fresh blocked run (the two blocks whose raw data is retained), support = 14 critic calls:

```
critic calls=14  ok=11  failed=3  (21.4%)

  TOKEN-WALL   empty_response           finish=length  rt=6000  ct=6000  contentChars=0     obs=29006ms
  TOKEN-WALL   empty_response           finish=length  rt=6000  ct=6000  contentChars=0     obs=27384ms
  TOKEN-WALL   invalid_structured_json  finish=length  rt=5887  ct=6000  contentChars=506   obs=25980ms
  => token wall = 3 (100%)   deadline = 0 (0%)
```

**Every failure is a token wall. Not one was a deadline kill.** The distinguishing
signature is exact: `reasoning_tokens = completion_tokens = 6000` — the model consumed
its entire budget on reasoning and the remaining content budget was **zero bytes**
(two calls) or a **506-byte truncated prefix** of the answer (one call).

These calls took 25.9–29.0 s **because** they generated 6,000 tokens. That is a
consequence of the token wall, not evidence of a deadline collision — which is
precisely the ambiguity Phase 1.6's summary table could not resolve.

Combining the earlier unblocked run (whose raw call rows were captured before the
probe's block numbering was fixed, and which this report treats as supporting rather
than primary evidence) gives the full Phase 1.7 sample:

| | calls | token wall | deadline | failure rate |
| --- | ---: | ---: | ---: | ---: |
| retained blocked run | 14 | 3 | 0 | 21.4% |
| earlier run, same code and config | 7 | 2 | 2 | 28.6% |
| **combined** | **21** | **5 (71%)** | **2 (29%)** | **33.3%** |

The combined 33.3% reproduces Phase 1.6's independent ~35% estimate and its 12-call
critic sample, so the two measurements agree on the size of the residual tail. The
deadline is therefore a **real but minority** contributor: 2 of 7 failures, and 0 of 3
in the higher-support retained run.

### 3.2 Success latency — is the 30,000 ms clamp binding?

Support = the 15 successful critic calls across both runs:

```
n=15   min=8,701ms   p50=19,140ms   p75=24,585ms   p90=28,734ms   max=29,739ms   clamp=30,000ms
within 20% of the clamp (>=24,000ms): 4/15 (27%)
within 10% of the clamp (>=27,000ms): 3/15 (20%)
```

```
buckets:   <10s: 0   10-20s: 6   20-27s: 3   27-30s: 2
```

So **~27% of SUCCESSFUL critic calls finish within 20% of the clamp**, and the slowest
success (29,739 ms) misses the clamp by 261 ms. The clamp is genuinely load-bearing —
but note what that means for each hypothesis:

- Under (a), raising `tokenBudget` toward 8,000 pushes the slow tail **past** 30,000 ms,
  converting token-wall failures into deadline failures while paying ~8 s more wall
  clock per attempt. Net failure rate: unchanged.
- Under (b), raising the clamp would recover only the deadline-killed calls — 2 of 21.

Both directions are dominated. The binding constraint at critic 6,000 is the **token
budget**, and it cannot be raised: 8,000 tokens at the measured rate needs ~35–38 s,
which the 30,000 ms clamp forbids. `critic 6,000` is therefore confirmed as the
configuration ceiling for this (provider, model) pair — exactly the Phase 1.6
conclusion, now with the mechanism identified rather than inferred.

### 3.3 Critic judgement is not what is losing candidates

```
judgements: accepted = 10 / 15   rejected = 5 / 15     (66.7% accept)
```

Consistent with Phase 1.6's 8/12 accept. **The critic's judgement is not the problem:
its OPERATIONAL failure is.** Two thirds of the candidates it gets to rule on, it
accepts.

### 3.4 Failure is candidate-specific, not spread evenly

```
{"n":4,"ap":4,"cr":4,"crf":0}  GitHub Advanced Security expands trial availability   <- 0 failures
{"n":4,"ap":1,"cr":1,"crf":0}  AI Scan for pull request APIs in public preview       <- 0 failures
{"n":4,"ap":2,"cr":2,"crf":2}  Enterprise managed permissions for GitHub Copilot...  <- fails
{"n":4,"ap":1,"cr":1,"crf":3}  MAI-Code-1-Flash deprecated                           <- fails 3/4
```

`MAI-Code-1-Flash deprecated` failed 3 of 4 critic calls, every one token-wall. The
tail is concentrated on candidates whose critique requires more reasoning — a bounded
re-sample is well matched to this shape (it re-rolls the sample, not the policy), but
the concentration also predicts a **non-zero residual** after re-sampling, because for
these candidates both rolls can hit the wall. Section 5 quantifies it.

## 4. Answer to T1's question

> N7 修复应该优先解决 deadline 还是 token？

**Token.** Not one of the retained failures was a deadline kill; all three were
`finish_reason=length` at exactly 6,000 completion tokens with 0–506 bytes of content.
The deadline contributed 2 of 21 failures overall, and the deepest successes (29.7 s)
show that raising the token budget would move failures *into* the deadline rather than
out of it.

> N7 修复应该走方案 i（重采样）、方案 ii（提高 deadline）、还是方案 iii（组合）？

**方案 i only — bounded critic operational re-sampling.** Consistent with the user's
pre-selection, now on evidence:

- **方案 ii is not justified.** It would recover at most 2 of 21 calls (9.5%), while
  changing a clamp that governs **every non-translation role** — a code change with a
  blast radius far larger than the defect it addresses.
- **方案 iii is not justified** for the same reason: there is no deadline-dominated
  failure population for a raised clamp to recover.
- **方案 i is well matched.** 71% of failures are pure sampling losses where the model
  never emitted a verdict at all, so the deterministic publication gate never saw a
  critique. Re-sampling restores a verdict to the gate without touching any gate.

**Not attempted, and why.** A direct measurement of "does critic 8,000 with a raised
deadline succeed, and in how long?" would turn the ~35–38 s extrapolation in §3.2 into
a measurement. It was out of T1's scope (it presumes a clamp change the user had not
authorised) and is recorded here as an open question rather than asserted as fact.

## 5. Consequence for 方案 i's sizing

With single-call failure probability `p`, one bounded re-sample takes the per-candidate
critic loss from `p` to `p²`:

| p (single call) | before | after 方案 i |
| --- | ---: | ---: |
| 0.21 (retained blocked run) | 21% | **4.5%** |
| 0.33 (combined Phase 1.7) | 33% | **11%** |
| 0.35 (Phase 1.6) | 35% | **12%** |

So 方案 i removes roughly two thirds to four fifths of the critic operational loss. It
does **not** eliminate it, and on the `MAI-Code-1-Flash deprecated`-shaped candidates
(both rolls can hit the wall) it will not remove it at all. The residual is legitimately
reported as `PROVIDER_EMPTY_RESPONSE` / `PROVIDER_TIMEOUT` and left as a failure —
never downgraded into a publication.
